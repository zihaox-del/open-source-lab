# Maintainer Playbook

## 维护原则

- 先确认真实需求，再写代码。
- 先交付最小闭环，再增加功能。
- 公开说明限制和失败，不用演示代替测试。
- 兼容性、安全性和维护成本与功能同等重要。

## 发布门槛

- 有明确的目标用户和问题陈述。
- 有可复制的安装与快速开始说明。
- 核心行为有自动化测试或稳定验证脚本。
- 有许可证、安全说明和变更记录。
- 没有敏感信息或权属风险。
- 至少有一条来自真实使用的反馈或实验记录。

## 版本节奏

- `0.1.0`：最小功能闭环，可供早期用户试用。
- `0.x`：接口仍可调整，每次变更写明迁移影响。
- `1.0.0`：核心接口稳定，维护和兼容承诺明确。

## 每周维护

1. 处理阻塞使用的问题。
2. 复核一个真实反馈或使用数据。
3. 合并一个小而完整的改进。
4. 更新状态、限制和下周唯一重点。
